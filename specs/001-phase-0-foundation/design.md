# Phase 0: Foundation and decision spikes

- Status: Draft for review
- Date: 2026-10-05
- Implements: ADR-0001, ADR-0003, ADR-0005, ADR-0007, ADR-0009, and the spike in ADR-0012
- Scope reference: ADR-0010, phase 0

## 1. Why this phase exists

Phase 0 builds no user features. It answers one question:

> **Can we build the product the ADRs describe, with the stack ADR-0005 chose, before we
> invest in features?**

It does this in two ways:

1. **It builds the skeleton every later phase depends on:** repository, toolchain, quality
   gates, the shared kernel, and the use-case registry that generates the CLI and MCP.
2. **It runs the spikes that could still change a decision.** Each spike ends with a
   written **go / no-go** result. A no-go reopens the ADR concerned *before* code is
   built on top of it.

- Any connection to a ServiceNow instance from product code. Spike S6 uses a separate,
  throwaway script.

## 6. Kernel design and its specifications

All kernel code is pure: no I/O, clock or randomness. Each bullet below is a **test name**.
Together they are the readable specification of the code.

### 6.1 Identifiers (branded types created by validating factories)

**`SysId`.** Same rule as v1: 32-hex ids, plus legacy out-of-box ids such as
`sysverb_query` or `Default view`.
- accepts a 32-character hexadecimal id
- accepts legacy ids made of letters, digits, underscores and inner spaces, up to 64
  characters
- rejects empty values, leading or trailing spaces, slashes, dots and ids longer than 64
  characters
- rejection raises `InvalidIdentifierError` with code `invalid-sys-id`

**`TableName`.** Pattern `[a-z0-9_$]+`.
- accepts `incident`, `sys_script_include` and `$table`-style names
- rejects uppercase, spaces, path separators and empty values

**`ScopeName`.** Safe as a path segment (v1 `path_segment` behavior).
- keeps names made of letters, digits, `_`, `.`, `$` and `-`
- converts unsafe names to a slug instead of failing (instance data can contain stray
  symbols)
- maps an empty scope to `global`
- never returns `.`, `..` or a value containing a path separator

### 6.2 Hash contract v1 (must match v1 byte for byte)

```
recordHash(class, fields) =
  sha256_hex( canonicalJson({ "class": class,
                              "fields": { k: canonicalText(v) for each field } }) )
```

**`canonicalText(value: string | null)`**
- converts CRLF and lone CR to LF
- strips all trailing LF characters, and nothing else (trailing spaces are kept)
- treats `null` as the empty string
- accepts only strings or null. v1 used Python `str()`, which turns booleans into
  `"True"`; the TypeScript type forbids non-strings so that difference can't occur.

**`canonicalJson(value)`.** Reproduces Python
`json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=True)`.
- sorts object keys by **Unicode code point**. JavaScript's default sort uses UTF-16
  code units, which differs for characters outside the Basic Multilingual Plane; a
  dedicated test covers this.
- uses no whitespace between tokens
- escapes every non-ASCII character as `\uXXXX` with lowercase hex, and characters
  outside the Basic Multilingual Plane as surrogate pairs (`é` → `é`,
  `😀` → `😀`)
- escapes control characters the way Python does (`\n`, `\t`, `\u0001`, …) and does not
  escape `/`

**`recordHash`**
- reproduces every vector in `tests/fixtures/hash-vectors.json`
- reproduces every vector in `hash-vectors-extended.json` (spike S1)
- gives the same hash for CRLF and LF versions of the same script
- does not depend on the order fields are supplied in
- changes when any field value changes (property test)

**Field exclusion.** These fields are never part of the hash: `sys_id`,
`sys_class_name`, `sys_mod_count`, `sys_updated_on`, `sys_updated_by`,
`sys_created_on`, `sys_created_by`, `sys_update_name`, `sys_scope`, `sys_domain`,
`sys_domain_path`, `sys_package`, `sys_tags`. This is the v1 `META_FIELDS` list. In
phase 0 it is a kernel constant; it is applied when artifacts are read (phase 1).

### 6.3 Errors (ADR-0003)

`SnagenticError` carries a stable `code`, a `message` and a `hint`, the next action for
the user or agent.

| Code family | Exit code |
|---|---|
| OK | 0 |
| Blocking findings | 1 |
| Usage | 2 |
| Precondition not met | 3 |
| Remote error | 4 |
| Not permitted | 5 |

- every error code maps to exactly one exit code
- an unknown or unexpected error exits with 70 and never prints credentials or stack
  traces in `agent` format

## 7. Use-case registry (ADR-0003)

The registry is the one place an operation is defined. Phase 0 proves the mechanism with
a single use case:

```ts
defineUseCase({
  name: "doctor",
  description: "Check that this machine can run snagentic: git, keychain, search index.",
  input:  z.object({ local: z.boolean().default(true) }),
  output: z.object({ checks: z.array(Check), ok: z.boolean() }),
  flags:  { readOnly: true, destructive: false, requiresDevelopmentInstance: false },
  mcp:    true,
  handler: runDoctor,          // calls probes through ports; no logic in generators
});
```

From this definition, phase 0 generates:
- the CLI command `snagentic doctor --local [--format agent|json|text]`, with exit code 0
  when every check passes and 3 otherwise, each failure carrying a hint;
- the MCP tool `doctor`, with input schema, output schema and the `readOnlyHint`
  annotation, served by `snagentic mcp` over stdio.

Specifications:
- the CLI and MCP produce identical JSON output for the same input
- adding a use case to the registry adds both the CLI command and the MCP tool, with no
  other code
- the MCP tool budget check fails when more than 12 use cases are marked `mcp: true`
- the generators contain no branching on use-case names (checked by a test)

The production-safety rule from ADR-0012 (write use cases absent for test and production)
needs instance profiles, so it is built in phase 1. The registry already carries the flags
it will use.

## 8. Architecture rules enforced from day one

`bun run arch` (dependency-cruiser) fails the build when:

1. code under `kernel/` or any `domain/` folder imports anything outside the kernel and
   domain, including Node or Bun built-ins (`fs`, `path`, `bun:*`, `process`);
2. `packages/core` imports from `packages/cli`;
3. the `registry/`, `cli/` or `mcp/` folders import adapters directly, instead of
   receiving them through ports;
4. any package imports another package's internals instead of its `index.ts`;
5. there is a circular dependency anywhere.

Each rule has a deliberately violating fixture in the test suite, which proves the rule
fires.

## 9. Spikes

Each spike produces `docs/spikes/Sn-<name>.md` with: question, method, raw measurements,
verdict (**go** / **no-go**), and the ADR it confirms or reopens.

### S1. Hash parity (ADR-0007)
- **Question:** does the TypeScript kernel produce exactly the v1 hashes, including edge
  cases?
- **Method:**
  1. Pass the five existing v1 vectors.
  2. Generate about 2,000 random records (Unicode, characters outside the Basic
     Multilingual Plane, control characters, CR/LF mixes, empty values, many fields).
  3. Compute their hashes **with the v1 Python code itself** (a small script run against
     `../snagentic`) and save them as `hash-vectors-extended.json`.
  4. The TypeScript tests must match all of them.
- **Go if:** 100% match.
- **No-go:** fix the kernel. The contract itself does not change.

### S2. YAML format (ADR-0007)
- **Background:** v1 writes YAML with PyYAML, using YAML 1.1 quoting rules
  (`yes`/`no`/`on` are quoted), escaped non-ASCII characters, wrapping at 100
  characters, and quoted strings for multi-line values. Reproducing PyYAML's output byte
  for byte in TypeScript is possible but fragile.
- **Question:** match PyYAML exactly, or define our own deterministic style?
- **Method:**
  1. Write a sample of v1 `record.yaml` and `_meta.yaml` files with both approaches.
  2. Compare the bytes, readability for agents, and the size of the git diff when
     switching.
- **Important:** hashes are computed from **values**, not YAML bytes, so either choice
  keeps change detection correct. The only cost of a new style is a one-time
  formatting-only rewrite of an existing v1 mirror.
- **Recommendation:** our own documented style (YAML 1.2, sorted keys, literal blocks
  for multi-line values), plus a one-time `snagentic migrate` commit.
- **Needs your decision.** See section 12.

### S3. Single binary on every platform (ADR-0005, ASR-05)
- **Question:** does `bun build --compile` produce a binary that works on all 5 targets,
  including the keychain add-on and SQLite FTS5?
- **Method:**
  1. In the CI matrix (macOS arm64, macOS x64, Windows x64, Linux x64, Linux arm64),
     compile and run `snagentic doctor --local --format json`.
  2. Record binary size and cold start time.
- **Linux note:** a desktop keychain (Secret Service) often isn't available on servers.
  CI uses environment variables for credentials there anyway (ADR-0004), so on Linux the
  keychain check may report `unavailable` with a hint rather than fail.
- **Go if:** all targets pass git and FTS5; keychain passes on macOS and Windows; cold
  start < 100 ms.
- **No-go fallback:** Node single-executable apps, or OS credential command-line tools in
  place of the native add-on.

### S4. Parsing real ServiceNow scripts (ADR-0005, ADR-0006)
- **Question:** can espree (the ESLint parser) parse real instance scripts?
- **Method:**
  1. Run it over a corpus of business rules, script includes, client scripts, UI
     actions and widget scripts, trying ES5 and then the latest ECMAScript version.
  2. Report the failure rate and categorize the failures.
- **Go if:** < 1% unparseable, with failures understood (for example, Rhino-era syntax).
- **No-go fallback:** a tolerant parser for the failing subset, or reopen the choice of
  parser in ADR-0005.
- **Needs input:** a corpus. The v1 repo contains no instance data. See section 12.

### S5. Hook latency (ASR-04)
- **Question:** can the compiled binary lint one changed file fast enough to run after
  every agent edit?
- **Method:** in the compiled binary, load the ESLint `Linter` with one sample rule and
  lint one real script. Measure 50 runs.
- **Go if:** p95 < 300 ms end to end.
- **No-go fallback:** route hook checks through the warm `snagentic mcp` process, or load
  the linter lazily.

### S6. Read-only production credential (ADR-0012)
- **Question:** does a user with `snc_read_only` really block writes through the REST
  API, and can that same user verify its own roles?
- **Method:** on your PDI, with a dedicated user that has `snc_read_only` plus read roles:
  1. Attempt create, update and delete through the Table API on a few tables; expect
     them to be refused.
  2. Check which system writes, if any, still happen (sessions, preferences).
  3. Query its own role assignments.
  4. Check which REST API access policy and OAuth scope options exist on your release.
- **Go if:** all business writes are refused, and the role check works with that
  credential.
- **Needs input:** your PDI and an admin to create the user. This can slip to the start
  of phase 1, but must finish before any production profile exists.

## 10. Continuous integration

| Workflow | Trigger | Steps |
|---|---|---|
| `verify.yml` | Every PR and push to `main` | `bun install --frozen-lockfile`, typecheck, lint, arch, test with coverage (≥ 90% for kernel) |
| `build.yml` | PRs touching `packages/` and manual runs | Matrix of 5 targets: compile, run `doctor --local`, upload the binary and measurements as artifacts |

Once you enable branch protection on `main`, `verify` becomes a required check.

## 11. Order of work (each step is one pull request)

1. D1 skeleton, plus `verify.yml`.
2. D2 kernel, with S1 (hash parity).
3. D3 + D4: registry, `doctor`, CLI and MCP generation.
4. D5 build matrix, with S3 (binaries) and S5 (latency).
5. S2 YAML comparison: report for your decision.
6. S4 parsing corpus, once the corpus is available.
7. S6 read-only credential, on your PDI.

Phase 0 is done when every item below holds:

- [ ] `bun run verify` passes in CI on `main`
- [ ] the binary runs `doctor --local` on all 5 targets
- [ ] S1, S3 and S5 are go (or ADRs reopened with your agreement)
- [ ] S2 has your decision recorded in an ADR-0007 amendment
- [ ] S4 and S6 are go, or scheduled with an agreed date before phase 1 work that
      depends on them
